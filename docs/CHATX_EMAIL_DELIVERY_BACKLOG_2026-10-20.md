# CHATX План реализации почты и внешней работы

Дата 20 октября 2026 года. Статус всех работ PLANNED. Основание — [подробная концепция](./CHATX_EMAIL_WORKFLOW_CONCEPT_2026-10-20.md). Документ переводит концепцию в очереди работ и критерии проверки. Номера ниже — идентификаторы требований и эпиков, а не созданные GitHub Issues. Сроки, бюджет и конкретные исполнители не назначены.

## Правила исполнения плана

1. Каждая работа получает отдельный объём, подтверждённые зависимости и проверяемый результат. Ветка runtime не включается только на основании принятия документации.
2. Task, Calendar, Pages, Decision, File, Request и Approval остаются существующими источниками рабочего состояния. Новые почтовые данные и отображения ссылаются на них.
3. Первый почтовый провайдер выбирается по реальной среде пилота. Второй провайдер не считается поддержанным после успешной проверки первого. Специфичные проверки обязательны для включённого адаптера; для невключённого фиксируется OUT_OF_SCOPE с причиной и проверяется отсутствие ложного обещания поддержки в UI. Это не PASS и не пропуск обязательного сценария выбранного провайдера.
4. UI может проектироваться параллельно с адаптерами. В рабочем приложении действия включаются только после готовности их серверных контрактов.
5. Для каждого эпика фиксируются scope, migration/backfill при необходимости, API, права, состояния ошибок, последствия отключения, тесты и наблюдаемые ограничения.
6. Приёмочные номера CXM-AT относятся к концепции. Пока сценарии не выполнены на конкретной сборке, их статус остаётся NOT RUN.

## Контракты передач между командами

| Передача | Передаваемый результат | Что проверяет принимающая команда |
|---|---|---|
| Product в UX | Термины, приоритеты, 26 экранов, роли и запрещённые смешения статусов | Наличие полного ручного пути без AI и всех ошибочных состояний |
| Domain в Connector | Typed source, идентичность, идемпотентность, права и границы команд | Ни одно поле провайдера не подменяет внутренний ID или роль |
| Connector в UI | Возможности, охват истории, статус и нормализованные ошибки | Интерфейс показывает частичный успех и отсутствие поддержки честно |
| Domain в Search и AI | Доступные версии источников и ограничения обработки | Текущие права проверяются перед выдачей и действием |
| Engineering в QA | Конкретный SHA, миграции, конфигурация, тестовые аккаунты и ограничения | Пройдены реальные переходы, включая повторы и восстановление |
| QA в Product | Фактические результаты и evidence по сценариям | Демонстрация и описание не превышают подтверждённую готовность |

## Приоритетные вертикальные сценарии

### Сценарий P1 Письмо и принятая работа

Подключить разрешённый тестовый ящик, получить письмо, открыть исходник, добавить внутреннюю заметку, создать задачу с допустимым исполнителем, подтвердить и выполнить её, приложить доказательство, принять результат, подготовить и отправить внешний ответ. Перезапуск сервера и повтор получения исходного письма не создают повторную задачу. Ответ остаётся в ожидаемой почтовой цепочке. После отзыва права старая вкладка не открывает источник заново.

### Сценарий P2 Команда и встреча

Два сотрудника работают с общим обращением, передают ответственность и готовят ответ. Согласующий утверждает конкретную ревизию; изменение адресата требует нового согласования. Внешний участник выбирает предложенное время, система повторно проверяет слот. Перенос одного вхождения серии сохраняет остальные встречи и сроки задач. Встреча получает реальный контекст и результаты через существующий процесс.

### Сценарий P3 Решение и управляемый помощник

Письмо является проверенным источником предложения. Пользователь с необходимыми правами подтверждает решение через расширенную Decision Authority. AI отвечает по разрешённым версиям и показывает источники. Инструкция внутри входящего письма не становится командой помощнику. Отзыв доступа прекращает дальнейшее раскрытие выдержек. Отправка ответа и изменение promisedAt требуют установленного подтверждения.

## Проверка документированной полноты

Концепция содержит 26 экранов, требования CXM-PROD-001–016, CXM-UX-001–054, CXM-ENG-001–064, CXM-BIZ-001–006, матрицу 17 продуктовых референсов и сценарии CXM-AT-001–068. Итого 140 требований: 16 + 54 + 64 + 6. Приёмочные сценарии и экраны посчитаны отдельно, поскольку это разные элементы документа.

Перед началом соответствующего эпика уточняются конкретные поля миграций и OpenAPI; перед выпуском заполняются фактические результаты проверок. Сохранённая концепция не присваивает статус PASS ни коду, ни провайдеру, ни production.
