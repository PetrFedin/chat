# ChatX — корпоративное рабочее пространство

`ChatX` — самостоятельное multi-tenant приложение компании: регистрация организации, сотрудники и роли, каналы и личные сообщения, задачи, календарь, файлы, голосовые сообщения, realtime-присутствие, уведомления, аудио/видеозвонки, Meeting Intelligence и связанный контур исполнения.

## Рабочий граф

`Organization -> Workspace -> People -> Conversation -> Message/Call -> Task/Meeting/File -> Calendar -> Execution -> Evidence -> Acceptance`

Для встреч этот же граф продолжается без отдельного «AI-блокнота»:

`Call -> Consent -> Recording -> Transcript -> Summary -> Proposed decision/action -> Human confirmation -> Task -> Evidence`

Одна сущность показывается в нужных рабочих контекстах, а не копируется между разрозненными модулями.

## Текущий исполняемый слой

- регистрация компании и владельца;
- password auth на `scrypt` + opaque HttpOnly sessions;
- приглашения сотрудников по ссылке;
- роли `owner / admin / manager / member / guest` и server-side RBAC;
- REST API + `/openapi.json`;
- WebSocket realtime для presence, typing и событий workspace;
- каналы, группы и direct messages;
- replies, reactions, mentions и server-side read cursor;
- Daily Work: unread, mentions, Notification Center, permission-aware global search и Files;
- local или S3-compatible object storage для файлов и voice;
- authenticated file downloads и inline preview для изображений, PDF и текста;
- browser MediaRecorder для голосовых сообщений;
- LiveKit-backed WebRTC/SFU audio/video calls;
- group calls, mic/camera controls, screen sharing и reconnect state;
- call state и participants хранятся в ChatX, а не в SFU;
- запись встречи через LiveKit Egress только после consent всех активных участников;
- evidence-first Meeting Intelligence: signed LiveKit webhook, durable jobs, timecoded transcript segments, summary, decisions/actions/risks/questions и source citations;
- Meeting Center с review-ready состоянием и переходом к конкретному фрагменту стенограммы;
- AI action не создаёт реальную задачу без отдельного подтверждения человеком;
- автоматический production worker для `transcribe` и `summarize` с durable claim, lease recovery, retry/dead-letter и graceful shutdown;
- optional audio-only transcription sidecar для длинных встреч, при этом MP4 остаётся review/evidence archive;
- provider-attempt telemetry: provider/model, attempt, request usage, latency и failure state без фиксации меняющейся цены в source event;
- Web Push infrastructure при настроенных VAPID-ключах;
- задачи и календарные события через тот же API;
- оргструктура: департаменты, отделы и группы деревом до 6 уровней, штатные
  слоты, ответственный за подразделение и делегирование управления веткой
  (`docs/ORG_STRUCTURE.md`);
- installable mobile-first PWA, RU/EN и dark/light themes;
- outbound webhooks: transactional outbox → подписанные HMAC-SHA256 доставки с
  retry, dead-letter и журналом (`docs/INTEGRATIONS.md`).

## Запуск

```bash
npm install
npm start
```

Откройте `http://localhost:3000` и зарегистрируйте компанию.

Без `DATABASE_URL` используется in-memory development store — данные сбрасываются
после рестарта, и в `NODE_ENV=production` сервер с таким хранилищем не поднимется.
Для постоянного режима задайте адрес базы и накатите схему:

```bash
export DATABASE_URL=postgres://...
npm run migrate          # применит всё, чего ещё нет
npm run migrate:status   # покажет, что уже накачено
```

Накатчик применяет каждую миграцию в своей транзакции вместе с отметкой о ней,
запоминает отпечаток файла (правка уже применённой миграции — это расхождение
между средами, и он о ней скажет) и берёт замок, чтобы два процесса не накатили
одно и то же дважды.

### Прогон тестов

```bash
export POSTGRES_TEST_URL=postgres://...   # база, которую тесты вправе пачкать
export VAULT_KEY="$(cat .secrets/vault.key)"
npm test
```

Тесты берут адрес из `POSTGRES_TEST_URL`, а при его отсутствии — из
`DATABASE_URL`. Отдельная переменная нужна, чтобы прогон не пошёл по рабочей
базе. Без обеих около трети набора — права, изоляция гостя, жизненный цикл
обязательств — молча помечается пропущенной, а итог выглядит зелёным, поэтому
**после прогона смотрите строку `# skipped`: она должна быть нулём.** База
должна быть накачена до последней миграции (`npm run migrate:status`): на
устаревшей схеме падает половина набора.

Дев-сервер, поднятый на той же базе, разбирает очереди вебхуков и почты
вместе с тестами — перед полным прогоном его надо остановить.

### Demo и persistence

Demo включается только явно:

```bash
DEMO_MODE=true
```

В memory-режиме Northstar Studio пересоздаётся после каждого рестарта. При одновременно заданных `DEMO_MODE=true` и `DATABASE_URL` тот же demo tenant хранится в PostgreSQL, повторный startup использует существующий workspace и не должен дублировать сотрудников, задачи, календарь или synthetic Meeting Intelligence.

Встроенные demo-файлы имеют fixture catalog: если PostgreSQL сохранился, а локальный ephemeral filesystem был очищен, эти демонстрационные SVG/Markdown/CSV могут быть восстановлены в прежние storage keys. Это **не** делает локальное файловое хранилище production-durable: обычные пользовательские загрузки и реальные записи встреч требуют S3-compatible storage.

`GET /healthz` отдельно показывает durability database и object storage. `persistence.durabilityConfigured=true` только когда authoritative database — PostgreSQL и выбран durable object-storage adapter. Это признак конфигурации durability, а не утверждение о полной production readiness остальных зависимостей.

## Реальные аудио/видеозвонки

Без LiveKit приложение продолжает работать, но `/join` честно отвечает `MEDIA_PROVIDER_UNAVAILABLE`. Для настоящих звонков настройте LiveKit Cloud или self-hosted LiveKit:

```bash
LIVEKIT_URL=wss://your-livekit-host
LIVEKIT_API_KEY=...
LIVEKIT_API_SECRET=...
```

Browser получает только short-lived participant token. `LIVEKIT_API_SECRET` никогда не отправляется клиенту. TURN/SFU transport обслуживается настроенной LiveKit-инфраструктурой.

## S3-compatible storage и запись встреч

Если `S3_BUCKET` не задан, обычные файлы сохраняются локально в `data/uploads` или `UPLOAD_DIR`. Такое хранилище считается недолговечным для production и на ephemeral hosting может быть очищено при redeploy/restart. Если `S3_BUCKET` задан — файловый adapter автоматически переключается на durable S3-compatible storage:

```bash
S3_BUCKET=chat-production
S3_REGION=ru-1
S3_ENDPOINT=https://s3.example.com
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_FORCE_PATH_STYLE=false
```

Для production-записи встреч дополнительно:

```bash
LIVEKIT_EGRESS_ENABLED=true
```

По умолчанию LiveKit Egress сохраняет один composite MP4 в тот же S3-compatible контур. Он остаётся архивом встречи и источником доказательства.

Для более лёгкого speech-to-text источника можно **явно** включить параллельный audio-only OGG sidecar:

```bash
LIVEKIT_TRANSCRIPTION_EGRESS_ENABLED=true
```

Это отдельный Egress и поэтому не включается скрыто. При включении ChatX хранит два связанных provider recording ID: MP4 archive и OGG transcription source. Если OGG готов — транскрипция предпочитает его. Если sidecar завершился ошибкой, но MP4 готов, pipeline детерминированно возвращается к MP4. Если MP4 упал, но OGG готов, транскрипция может продолжиться, при этом архив встречи честно остаётся в состоянии `failed`.

`egress_ended` принимается только через подписанный LiveKit webhook. Job создаётся один раз при появлении первого пригодного transcription source.

## Meeting Intelligence provider runtime

Provider selection сделан явным. Наличие API key само по себе ничего не включает: если provider variables не заданы, pipeline остаётся fail-closed и не создаёт фиктивные стенограммы/summary.

Для OpenAI transcription + summary:

```bash
OPENAI_API_KEY=...
MEETING_TRANSCRIPTION_PROVIDER=openai
MEETING_SUMMARY_PROVIDER=openai

# optional
OPENAI_TRANSCRIPTION_MODEL=gpt-4o-transcribe-diarize
OPENAI_MEETING_SUMMARY_MODEL=gpt-5.6
OPENAI_MEETING_SUMMARY_REASONING=low
MEETING_TRANSCRIPTION_LANGUAGE=ru
MEETING_TRANSCRIPTION_TIMEOUT_MS=180000
MEETING_SUMMARY_TIMEOUT_MS=180000
```

Transcription adapter запрашивает `diarized_json` и `chunking_strategy=auto`, затем сохраняет speaker-labelled segments с `startMs/endMs`. Summary adapter использует Responses API + strict JSON Schema и отправляет `store:false`. Все предложения дополнительно фильтруются repository layer: proposal без существующего transcript segment source не материализуется.

Worker включён по умолчанию в обычном server runtime, но выполняет работу только для реально настроенных providers:

```bash
MEETING_WORKER_ENABLED=true
MEETING_WORKER_POLL_MS=1500
MEETING_WORKER_PROVIDER_WAIT_MS=30000
MEETING_WORKER_SHUTDOWN_MS=5000
```

Несколько экземпляров приложения могут polling-ить одну PostgreSQL queue: claim использует `FOR UPDATE SKIP LOCKED`, а lock token + bounded lease не дают двум workers подтвердить один job. При аварийном завершении stale processing job восстанавливается после lease timeout.

## Processing safety и экономика

Текущий provider adapter принимает media bytes как multipart body, поэтому ChatX вводит собственный fail-safe до загрузки крупного объекта в память:

```bash
MEETING_PROCESSING_MAX_IN_MEMORY_BYTES=67108864
```

Default — 64 MiB. Object storage сначала проверяется через `head()`. Если выбранный archive/sidecar превышает лимит, job завершается контролируемой ошибкой `RECORDING_OBJECT_TOO_LARGE`; provider не вызывается и приложение не пытается неограниченно аллоцировать RAM. Для длинных встреч предпочтителен audio-only sidecar.

Каждый фактический внешний provider attempt записывается отдельно в `meeting_provider_calls`: `provider`, `model`, `attempt_number`, provider request ID, source metadata, provider-reported `usage`, latency и failure state. Повторная попытка не перезаписывает предыдущую.

Денежная стоимость намеренно не зашивается в историческую provider-call запись: тарифы меняются. Экономика должна рассчитываться из сохранённого usage через версионированный price catalog, чтобы историческая себестоимость была воспроизводимой.

Пользовательский Meeting Center получает безопасные операционные метрики, но не provider request IDs и не внутренние source metadata.

`GET /healthz` показывает webhook, processor и worker state, а также отдельный `persistence` блок: durability базы, durability object storage и итоговый `durabilityConfigured`.

## Security boundary

- пароли: `scrypt` + индивидуальная случайная salt;
- в БД хранится только SHA-256 hash session token;
- cookie: `HttpOnly`, `SameSite=Lax`, `Secure` в production;
- RBAC проверяется на серверной границе;
- private conversation realtime, calls, files, transcripts и proposals доступны только соответствующему audience;
- LiveKit room имеет opaque name, не раскрывающий workspace ID;
- LiveKit join credential короткоживущий и выдаётся только authenticated member;
- consequential call recording требует server-side consent всех активных участников;
- LiveKit webhook проверяется официальным JWT + exact-body SHA contract;
- запись валидируется в object storage до transcription, а SHA-256 фактически выбранного source сохраняется в intelligence run;
- AI proposals не являются authoritative work: responsibility, promised date и создание task подтверждаются человеком;
- ChatX/PostgreSQL остаётся authoritative для lifecycle и work graph; LiveKit отвечает за media transport/Egress, AI provider — только за предложенную интерпретацию доказательств.

## Приём компании: реквизиты и штат списком

При регистрации спрашивают четыре вещи — название, имя владельца, почту и
пароль — и ещё три необязательных под раскрытием: юридическое лицо, ИНН и
почтовый домен. Обязательными они быть не могут: человек, который пришёл
попробовать, не должен искать ИНН, чтобы завести пространство. Дозаполнить
их можно в «Ещё → Компания», там же адрес, сайт и телефон.

Почтовый домен нужен не для красоты: по нему при приглашении сразу видно
чужой адрес — `ivanov@gmail.com` среди `@granit.ru` обычно опечатка. В
форме приглашения под полем появляется предупреждение, в списке такая
строка помечается «чужой домен». Это предупреждение, а не отказ: гостя —
подрядчика, заказчика — зовут именно с чужого адреса, и у роли «гость»
предупреждения нет вовсе.

Штат заводится списком: «Ещё → Пригласить → Пригласить списком». Туда
вставляют то, что выгрузили из таблицы — по строке на человека, адрес и
через запятую роль (`владелец`, `админ`, `руководитель`, `сотрудник`,
`гость`); роли нет — значит сотрудник. До 200 строк за раз.

Третий столбец — подразделение, по названию из схемы: человек попадает в
отдел и в его комнату сразу, а не вторым проходом по тому же списку через
неделю. В закрытое подразделение можно звать, только если сам в нём
состоишь: иначе приглашение стало бы обходом — вписать кого угодно в
закрытый отдел нельзя, а позвать туда письмом было бы можно.

Отдел мог за неделю, пока шла ссылка, распуститься или набиться до отказа.
Тогда человек всё равно входит в компанию — просто без отдела, и об этом
остаётся запись в журнале: молча потерять распределение хуже, чем сказать.

Разбор построчный, и в этом весь смысл: одна кривая строка не отменяет
остальные. Каждая строка возвращается со своим итогом — «приглашён», «уже
здесь», «повтор в списке», «не адрес», «неизвестная роль», «права выше
ваших», — в том же порядке, в каком её вставили, чтобы сверять глазами со
своей таблицей. Ссылка-приглашение приходит в ответе сразу: если почта в
компании не настроена, её разошлют руками.

## Проще войти: рабочая почта вместо очереди к администратору

Заводить каждого сотрудника руками — сорок действий администратора и
сорок человек в очереди. Поэтому у компании есть домен и число мест, а
сотрудник заводится сам.

Как это устроено:

1. Компания в «Ещё → Компания» указывает почтовый домен, число мест и
   включает «Сотрудники заводятся сами».
2. На входе сотрудник жмёт «Меня ещё не завели — войти по рабочей почте»
   и вводит свой адрес.
3. Если домен совпал и места есть — на почту уходит **та же
   ссылка-подтверждение**, что и у обычного приглашения. Дальше всё как
   всегда: имя, пароль, вход. Отдельного кода принятия не появилось, и
   проверен он один раз.

Ответ на этом экране **всегда один и тот же** — и когда компания нашлась,
и когда нет. Иначе адрес превращается в справочник «а пользуется ли ChatX
компания такая-то», а это не тот вопрос, на который стоит отвечать
посторонним.

Самостоятельный вход всегда даёт роль сотрудника — не больше. Мест не
осталось — человеку писать нечего, а вот владельцу есть: письмо уходит
ему, потому что добавить места может только он.

Дальше сотрудник находится по имени и фамилии в поиске и в списке людей и
добавляется в беседы, группы, встречи и звонки как все остальные.

## Кого позвали и кто ещё не пришёл

Позвав сорок человек списком, узнать, кто из них дошёл, было неоткуда:
приглашения жили только в письмах. Через неделю пригласивший не помнит,
кому слать повторно, и зовёт заново всех — а человек получает второе
письмо и думает, что первое было подделкой.

В «Пригласить» под формой список ожидающих: адрес, роль, подразделение,
кто позвал и не вышел ли срок. Рядом две кнопки. «Отозвать» — ссылка
перестаёт работать сразу. «Позвать заново» — для письма, которое не дошло
или попало в спам: уходит новая ссылка, а прежняя закрывается, потому что
две живые ссылки на один адрес это два входа, и закрывать потом придётся
обе. Оба действия — для того, кто позвал, или для того, кто распоряжается
составом компании.

Там же видно, сколько мест осталось.

Закрытое подразделение в этом списке не называется тому, кто в нём не
состоит: иначе список приглашений обходил бы его закрытость.

## Места в компании

Компания объявляет число мест в «Ещё → Компания». Занятым считается не
только сотрудник, но и **неотвеченное приглашение**: иначе в компанию на
десять мест зовут пятьдесят человек, все получают ссылку — и сорок
упираются в стену уже на входе, когда отказываться поздно и неловко.

Гости мест не занимают: подрядчик приходит на одну работу и уходит, и штат
компании от этого не растёт.

Предел держат все три входа. Поштучное приглашение отвечает отказом, где
названо, сколько мест ушло на людей и сколько на приглашения. Список
отмечает строку «мест не осталось» и идёт дальше — за ней могут стоять
гости, которым место не нужно. Самостоятельный вход по домену письма не
шлёт, а сообщает владельцу, что мест не хватило.

Отозванное приглашение место возвращает.

## Закрытые подразделения

Юридический отдел, служба безопасности, группа под сделку — там сам список
участников и есть тайна. Подразделение заводится закрытым переключателем в
его форме.

Уговор простой:

- **снаружи видно** имя, замок и число людей — за места платит компания, и
  прятать сам факт существования нельзя;
- **изнутри видно** всё: состав, назначение, руководителя и комнату;
- **состав меняют только изнутри** — руководитель подразделения и
  назначенные им администраторы. Права на всё пространство сюда не годятся:
  возможность вписать в закрытый отдел кого угодно — в том числе себя — это
  и есть доступ к нему, и владелец такой возможности не имеет.

Поэтому же закрытое подразделение заводит не только владелец, но и любой
руководитель (право `org.unit.private.create`): если бы закрытую группу мог
создать только владелец, закрывать было бы не от кого.

Что владелец всё-таки может: переименовать подразделение и распустить его.
Распустить — значит вместе с составом: вывести оттуда людей он не может,
потому что их не видит, и без этого закрытый отдел стал бы неразрушимым, а
места в нём — навсегда занятыми. В журнале остаётся имя и число
освобождённых мест — не имена.

Карточка человека закрытых подразделений не выдаёт: иначе состав закрытого
отдела собирался бы по одному сотруднику за раз.

## Подразделение — это место работы, а не строчка

У каждого подразделения есть своя закрытая беседа, и состав подразделения
и состав беседы — одно и то же: вошёл в отдел — вошёл в комнату, вышел —
вышел. Ничего отдельного для неё не написано: это обычная комната, поэтому
непрочитанное, упоминания, закреплённое, поиск и уведомления работают в ней
сами.

Из этого получается то, ради чего всё и затевалось: человек в четырёх
отделах видит их первым блоком в «Оргструктуре» — «Мои подразделения», с
числом непрочитанного в каждом и входом одним нажатием. Ниже — «Вся
компания» со схемой целиком.

## Оргструктура

Компания описывается деревом подразделений: `компания → департамент → отдел →
группа`, до шести уровней. У подразделения есть плановая численность
(`seatLimit`) и ровно один ответственный. Плановая численность — ограничение, а
не подпись: посадить сверх плана нельзя, опустить план ниже фактического
состава нельзя.

Управление делится надвое. Право `org.structure.manage` (owner и admin)
перестраивает компанию целиком. Руководитель или администратор подразделения
управляет **своей веткой** — составом, подгруппами, назначением ответственного
— но не переносит своё подразделение и не меняет плановую численность. Так
начальник отдела набирает людей, не получая прав на весь workspace.

Цепочка подчинения выводится из дерева, а не хранится у человека: перенос
подразделения переносит и линию подчинения, поэтому они не могут разойтись.
Гость на оргсхему не попадает — он сотрудник другой компании.

Подробности и таблица прав — `docs/ORG_STRUCTURE.md`.

## Исходящие интеграции

Работа отдаётся наружу одним подписанным потоком событий, а не адаптером на
каждую систему: Telegram-бот, CRM и корпоративный портал потребляют одну и ту
же доставку. Endpoint регистрируется через `POST /api/v1/integrations/webhooks`
(право `integration.manage`, то есть owner и admin), секрет показывается
ровно один раз при создании.

Доставка подписана `x-chat-signature: v1,t=<unix>,s=<hmac-sha256>` над строкой
`<timestamp>.<raw body>`; timestamp входит в подпись, поэтому перехваченную
доставку нельзя переиграть позже. Retry — экспоненциальный с jitter, до 6
попыток; 4xx кроме 408/429 считается окончательным отказом получателя.
Доставка гарантируется **как минимум один раз** — дедуплицируйте по
`x-chat-event-id`.

Очередь разбирается честно: порядок — по кругу между приёмниками, а не по
времени создания, и на одного приёмника работник держит не больше своей доли
одновременных доставок. Медленный получатель занимает свои места, а не всю
очередь. Адрес проверяется не только при заведении подписки, но и перед
каждой отправкой — имя, начавшее указывать внутрь сети, дальше не пойдёт.
Приёмник, не отвечающий `WEBHOOK_ENDPOINT_FAILURE_LIMIT` раз подряд (по
умолчанию 20), отключается сам; владелец включает его обратно, и счётчик
обнуляется.

Настройки работников (все необязательны): `WEBHOOK_WORKER_ENABLED=false`
останавливает рассылку, `WEBHOOK_WORKER_POLL_MS`, `WEBHOOK_WORKER_BATCH`,
`WEBHOOK_WORKER_CONCURRENCY`, `WEBHOOK_WORKER_PER_ENDPOINT`,
`WEBHOOK_DELIVERY_TIMEOUT_MS`, `WEBHOOK_DELIVERY_LEASE_MS`. Аналогично
`MEETING_WORKER_ENABLED` и `MEETING_JOB_LEASE_MS` для обработки совещаний,
`REMINDER_WORKER_ENABLED` и `REMINDER_WORKER_POLL_MS` — для напоминаний.

Без `DATABASE_URL` маршруты отвечают `503 INTEGRATIONS_UNAVAILABLE`:
in-memory store не даёт durable-очереди, а webhook без retry хуже,
чем его отсутствие.

Подробности, схема payload и референсный верификатор — `docs/INTEGRATIONS.md`.

## Внутри обязательства: шаги, помощники, связи

Три таблицы под это лежали в схеме с первого дня без единой строки кода.

**Шаги** (`task_checklist_items`) — потому что одно обещание с пятью
шагами честнее пяти обещаний: человек обещал одно дело и отчитывается за
него. Счётчик «сделано из всего» виден в списке задач, а не только
внутри карточки.

**Помощники** (`task_collaborators`) — потому что отвечает один, а делают
обычно вдвоём. Соисполнитель видит задачу, находит её в своём списке и
отмечает шаги сам; отвечает за результат по-прежнему `owner`. Ради этого
`canViewTask` признаёт четвёртого участника — иначе помощь была бы
формальной: человека вписали, а открыть задачу он не может.

**Связи** (`task_dependencies`) — потому что отчёт умеет показать
застрявшее, но не может объяснить, чего оно ждёт. Круг запрещён
рекурсивным запросом: цепочка «A ждёт B, B ждёт C, C ждёт A» — это не
зависимость, а три обязательства, которые никогда не сдвинутся.

Ещё семь таблиц — `projects`, `project_members`, `teams`, `team_members`,
`calendar_blocks`, `device_registrations`, `message_receipts` — убраны
миграцией 034 вместе с висячей колонкой `commitments.project_id`. За ними
тоже не было кода, но, в отличие от трёх выше, они дублировали уже
работающее (оргструктуру, события календаря с `kind='focus'`,
`push_subscriptions`) или предлагали дорогое решение дешёвого вопроса
(«кто прочитал» считается из отметок прочтения беседы, а не строкой на
каждое сообщение на каждого участника). Пустая таблица — не безобидный
задел: она врёт следующему разработчику, что фича почти готова.

## Отчётность по обязательствам

`GET /api/v1/tasks/report?from=&to=&scope=team|mine`. Продукт стоит на
мысли, что задача — это обещание одного человека другому, и до сих пор
не мог ответить ни на один вопрос, который из неё следует. Теперь
отвечает: доля обещаний, закрытых в обещанный срок, кто сейчас
перегружен, что застряло без движения дольше недели и кто кого просит.

Момент закрытия хранится в `commitments.closed_at` (миграция 031, с
точным backfill из журнала аудита): `updated_at` для этого не годится —
он сдвигается от любой правки, в том числе через месяц после закрытия.

Кто ведёт чужие задачи (`task.manage.team`) — видит компанию; остальные
видят себя, даже если попросят `scope=team`. Гость обязательств не
носит и отчёта не получает.

Считаем намеренно скучно: ни «продуктивности», ни баллов, ни рейтинга
сотрудников. Доля «в срок» не показывается как ноль, когда сроков никто
не обещал, — это разные утверждения.

## Кто на месте: статусы доступности

Присутствие в продукте было техническим — в сети, отошёл, — то, что
вычисляет само приложение по сокету. Но на работе спрашивают не «онлайн
ли Нина», а «когда она вернётся», и ответить на это может только она
сама.

Рядом с техническим состоянием появилась объявленная доступность:
короткий набор понятных слов (на встрече, на обеде, не отвлекать, буду
позже, на больничном, в отпуске, в командировке) и момент возвращения.
«Буду завтра в десять» и «вернусь пятого с двух» — это одно и то же поле
`back_at`, просто разный момент.

Два решения. Объявленное не стирается отметкой присутствия: приложение
шлёт только состояние, и закрытая крышка ноутбука не отменяет отпуск.
И статус гаснет сам по `back_at` — «на обеде до 14:00» не висит до
вечера, и никакой сборщик для этого не нужен.

## Дни рождения и нерабочие дни

День рождения хранится без года: поздравить нужно в правильный день, а
возраст — не то, что человек обязан сообщать работодателю, чтобы
получить поздравление. Отсюда и проверка «31 февраля» на входе, и
пропуск 29 февраля в невисокосный год — придумывать за человека другую
дату значит поздравлять не тогда.

Праздники и переносы — не события, которые кто-то заводит: это
производственный календарь страны, один на всех в пространстве. Годы
перечислены явно, а не выведены правилом: переносы объявляются
постановлением каждый год, и формула даёт неверный календарь, который
хуже отсутствующего; про год, о котором данных нет, мы честно отдаём
только постоянные даты. Своя запись в `workspace_holidays` перекрывает
встроенную — компания может работать в праздник или объявить свой
нерабочий день.

Оба слоя включаются на всю компанию (`show_birthdays`, `show_holidays`):
нерабочий день одинаков для всех, кто здесь работает. В сетке они
рисуются строкой, а не кнопкой — открывать у них нечего.

## Настройки уведомлений

Уведомления были устроены по принципу «всё или ничего»: ни тихих часов,
ни выбора, о чём присылать. В пространстве с сорока каналами это первая
причина выключить их совсем — и вместе с рекламой чужого канала человек
перестаёт получать упоминания и просроченные сроки, то есть ровно то,
ради чего уведомления и нужны.

Шесть переключателей по смыслу, а не по типам событий («меня упомянули»,
а не `message.mentioned`), и тихие часы по местному времени человека.
Интервал может переходить через полночь — «с 22 до 8» встречается чаще,
чем «с 9 до 18», и наивное `from <= h < to` даёт на нём пустой
промежуток. Из тишины есть один выход, и он обязан быть: человека
позвали лично; иначе тихие часы означают «я недоступен», а это другое
обещание.

Настройки применяются в единственном месте — воронке push
(`notifyUsers`): фильтровать в каждом вызывающем значит однажды забыть, и
тогда выключенный переключатель окажется враньём. Список уведомлений
внутри приложения остаётся полным: это журнал, а не окрик.

Отправку push теперь можно подменить (`options.sendPush`) — без этого шва
проверить, что выключенный переключатель действительно останавливает
уведомление, нельзя ничем, кроме веры.

## Черновики сообщений

Набранный и неотправленный текст пропадал при переходе в другую беседу.
Черновик лежит в браузере, а не на сервере, и намеренно: неотправленный
текст — самое личное, что есть у человека в рабочем пространстве, и
отправлять его в чужую базу ради синхронизации между устройствами
— плохой обмен. Ключ включает рабочее пространство, так что два
пространства в одном браузере не видят черновиков друг друга.

В списке бесед черновик показывается вместо последнего сообщения —
иначе о нём вспоминают, только снова открыв беседу.

## Экран телефона

Продукт обязан помещаться в 375 точек — это ширина iPhone, и на ней
проверяется всё. Четыре причины переполнения, найденные измерением в
браузере, а не на глаз:

* `.stack` был гридом с колонкой `auto`, то есть растягивался до самого
  широкого ребёнка: длинная строка внутри `.row` распирала карточку до
  594 точек. Теперь колонка `minmax(0,1fr)`;
* внутри `.row` то же самое делала колонка `auto` без `min-width:0` —
  `.row-sub` не переносится, и её полная длина становилась шириной
  строки;
* кнопки действий не помещались рядом с текстом и вылезали за край,
  утаскивая за собой горизонтальную прокрутку всей страницы. На узком
  экране они переносятся под текст;
* ряды фильтров и девять кнопок в шапке беседы уезжали в боковую
  прокрутку. Последними — то есть невидимыми — оказывались звонки.
  Теперь переносятся: прятать главное действие за жестом, о котором
  никто не сказал, нельзя;
* колонки `repeat(N,1fr)` не сжимаются ниже содержимого — длинное слово
  в плитке распирало сетку шире экрана на 320 точках. Везде
  `minmax(0,1fr)`.

Боковой прокрутки нет нигде и ни при какой ширине — это правило, а не
наблюдение: `.modal`, списки ящиков и панель совещаний прокручиваются
только вертикально (`overflow-x:hidden`), а полосы, которые раньше
ехали вбок, переносятся. Проверено измерением на 320, 375 и 390 точках:
ни страница, ни один вложенный ящик не прокручиваются горизонтально.

Проверки в `test/mobile-fit.test.js` буквальные: каждая поставлена на
измеренное переполнение. Статическая проверка не заменяет взгляда на
экран, но ловит возврат ровно этих правок — вёрстку никто не открывает
на телефоне до жалобы.

## Повторяющиеся встречи

Колонка `recurrence_rule` лежала в схеме с первого дня, и кода за ней не
было ни строки: еженедельную планёрку — самую частую встречу вообще —
заводили руками каждую неделю.

Правило хранится подмножеством RFC 5545 (`FREQ`, `INTERVAL`, `BYDAY`,
`COUNT`, `UNTIL`) — это формат, на котором говорят все календари, и его
можно отдать наружу, не выдумывая своего. Вхождения намеренно **не**
материализуются строками: серия «каждый понедельник, без конца» — это
бесконечное число строк, и правка заголовка потребовала бы переписать
их все. В базе лежит одно событие, вхождения раскрываются на чтение
внутри запрошенного окна и приходят под составным признаком
`событие@момент`.

Два места, где наивная реализация врёт молча. Перевод часов: «каждый
вторник в 10:00» считается по календарным суткам в поясе встречи, а не
прибавлением семи суток в миллисекундах, — иначе после перевода планёрка
съезжает на час. И 31-е число: месяцы без него пропускаются, как велит
RFC, а не сдвигаются на 28-е — сдвинутая встреча оказывается не там, где
её ждут.

Отличия одной встречи от серии живут в `calendar_event_exceptions`
(миграция 033): отменили планёрку на праздники — строка «вхождение
отменено», перенесли на час — строка с новым временем. Правило при этом
не трогается. `POST /api/v1/calendar-events/{id}/occurrences/{at}`
отменяет или переносит одну, `DELETE` возвращает её в строй.

## Учётная запись: пароль и входы

Двух вещей у учётной записи не было вовсе. Сменить пароль изнутри было
нельзя — оставалось «я забыл пароль»: выйти, просить письмо, ждать. И
утёкший сеанс отозвать было нечем: список входов не показывался нигде, а
«Выйти» закрывал ровно тот сеанс, из которого нажали, — украденный
ноутбук оставался внутри до истечения срока.

`GET /api/v1/auth/sessions` показывает устройство, адрес и когда заходили,
с пометкой текущего; `DELETE /api/v1/auth/sessions/{id}` закрывает один,
`POST /api/v1/auth/sessions/revoke-others` — все, кроме текущего (именно
кроме: человек, у которого украли телефон, не должен вылететь сам).
`POST /api/v1/auth/password` меняет пароль, спрашивает старый и закрывает
все остальные входы; попытки ограничиваются так же, как вход.

## Realtime: пределы сокета

Сокет открыт всякому, кто вошёл, и стоит дорого: пакет «печатает» — это
два запроса к базе и рассылка всем в беседе. Кадр ограничен 16 КиБ
(`ws` по умолчанию принимает до ста мегабайт), поток служебных пакетов —
`WS_PACKETS_PER_SECOND` (по умолчанию 20) на соединение; лишние молча
отбрасываются, а не караются разрывом. Ошибка протокола приходит
событием `error` на сокет — слушателя не было, и она становилась
необработанным исключением всего процесса.

## Приём нового человека

Новый сотрудник попадал в оболочку с чужими каналами, нулями на экране
«Сегодня» и без единого объяснения, почему задача здесь — это обещание,
а не пункт списка. С устройством продукта он знакомился единственным
способом: спрашивал коллегу.

`GET /api/v1/onboarding` отдаёт список первых шагов, и ни один из них не
отмечается нажатием: заполнена ли должность, открывал ли человек хоть
один канал, писал ли он что-нибудь, есть ли у него первое
обязательство. Мастер настройки с галочками, которые ставит сам
пользователь, врёт с первого экрана.

Отдельно стоит отметить, почему шаг про каналы считается по отметке
прочтения, а не по членству: членство в открытых каналах выдаётся само в
момент появления человека в пространстве, и шаг был бы закрыт ещё до
того, как новичок увидел первый экран.

Карточка уходит сама, когда все шаги сделаны или прошло две недели;
`POST /api/v1/onboarding/dismiss` убирает её раньше.

## Каталог каналов

`GET /api/v1/conversations/catalogue?q=` — открытые каналы компании с
описанием, числом участников и активностью за месяц. Список названий в
боковой панели перестаёт быть ответом на «что здесь есть» примерно на
тридцати каналах. Приватные каналы в каталог не попадают: само их
существование — тоже сведения.

`POST /api/v1/conversations/{id}/join` — вход обратно. Уйти из канала
было можно, вернуться — нет: маршрута не существовало, и человек
оставался «здесь по видимости», без строки участника и без счётчика
непрочитанного.

## Поиск по содержимому файлов

Имя файла приезжает в заголовке HTTP, где нельзя ничего, кроме латиницы,
поэтому клиент кодирует его процентами. Разбор терпимый к двум обычным
случаям: процент в самом имени («Скидка -50%.pdf» — нормальное имя отчёта,
а не ошибка) и клиент, который не кодирует вовсе (curl, чужой скрипт) —
тогда байты UTF-8, прочитанные как latin-1, складываются обратно.

Файл находится не только по имени, но и по тому, что внутри. При загрузке
из него извлекается текст и кладётся в тот же индекс, что и сообщения.

Что читается: простой текст, `docx`, `xlsx`, `pptx` и PDF с текстовым слоем.
PDF разбирается своим кодом (`src/search/pdf-text.js`), без внешних
зависимостей: находим объекты перебором, разворачиваем потоки, читаем
таблицу `ToUnicode` у каждого шрифта и ведём перо по ширинам начертаний —
пробелов в PDF нет, и место слова определяется по просвету между буквами.

Что не читается и чем не притворяется:

- **сканы** — вместо букв картинка, нужен распознаватель;
- **файлы под паролем** — потоки зашифрованы, открыть их нечем;
- **шрифт без `ToUnicode` с нелатинскими кодами** — что значит код, знает
  только эта таблица, и выдумывать буквы хуже, чем не выдать ничего.

Такой файл остаётся в поиске по имени. Разбор никогда не роняет загрузку:
непрочитанный файл — это файл без текста в индексе, а не отказ его принять.

Границы: не больше 25 МБ на файл, 200 000 знаков текста с него и полсекунды
на разбор PDF. Предел по времени нужен потому, что разбор идёт прямо в
обработчике загрузки, пока файл в руках, а сервер однопоточный: без него
многосотстраничная выгрузка держала бы всех остальных несколько секунд.
Полсекунды хватает документу мегабайта на три — это все договоры, акты и
счета; что не успели прочесть, просто не попадает в индекс
(`TIME_BUDGET_MS` в `src/search/pdf-text.js`).

## Сводка «что я пропустил»

`GET /api/v1/digest?from=`. Вопрос понедельника после недели
отсутствия, на который продукт отвечал единственным способом — листайте
всё подряд. У кого сорок бесед, тот не листает, и пропущенное пропадает
совсем.

Без `from` граница — последняя отметка предыдущего сеанса этого
человека (`user_sessions.last_seen_at`), то есть буквально «пока меня не
было»; если прошлого сеанса не осталось, отступаем на неделю. Слишком
давняя граница обрезается девяноста днями: сводка за полгода — это та
же лента, только в другом порядке.

Разделы отвечают только на «что касается лично меня»: упоминания,
предложенные обязательства без ответа, приглашения на встречи, сроки,
прошедшие внутри отрезка, движение обязательств, сделанное кем-то
другим (по строке на обязательство, а не на каждый переход), прошедшие
встречи, беседы с наибольшим приростом и новые люди в компании. Гость
получает ту же сводку, но только по тому, что ему видно.

## Почта

Приглашение в компанию и ссылка на смену пароля уходят письмом. До этого
канала их передавали руками: администратор копировал ссылку из ответа API
и отправлял её в мессенджере, а человек, забывший пароль, не мог сделать
ничего сам — приходилось ждать того, кто уже внутри.

Письма ставятся в durable-очередь (`mail_messages`) и уходят отдельным
работником: аренда с токеном, повторы с растущим отступом, мёртвая буква
вместо вечного перезапуска — как у доставок вебхуков и по тем же
причинам. Отказ `5xx` («такого ящика нет») не повторяется: это жжёт
попытки и репутацию отправителя. Не дошедшее письмо попадает в журнал
аудита событием `mail.undelivered` — иначе непришедшее приглашение
выглядит для компании как «человек не отвечает».

Маршрут `POST /api/v1/password-resets/request` принимает просьбу о смене
пароля без входа и **всегда** отвечает `204`, есть у нас такой адрес или
нет: иначе по нему перебирают, кто работает в компании. Попытки
считаются в базе по адресу (`PASSWORD_RESET_LIMIT`, по умолчанию 3 за
`PASSWORD_RESET_WINDOW_MS` = час) и по источнику — общим ограничителем
входа.

Настройка: `MAIL_HOST`, `MAIL_PORT` (587), `MAIL_SECURE=true` для TLS
сразу вместо STARTTLS, `MAIL_USER`, `MAIL_PASSWORD`, `MAIL_FROM`,
`MAIL_FROM_NAME`, `MAIL_HELO`, `MAIL_RETURN_PATH`,
`MAIL_MESSAGE_ID_DOMAIN`, `MAIL_CA`, а также `MAIL_WORKER_ENABLED=false`,
`MAIL_WORKER_POLL_MS`, `MAIL_WORKER_BATCH`, `MAIL_LEASE_MS`.

Пароль от почтового ящика уходит только по шифрованному соединению: если
сервер объявляет `STARTTLS`, клиент поднимает шифр и здоровается заново, и
только после этого представляется. Проверка подлинности сервера не
отключается ничем — у собственного почтового сервера внутри компании
сертификат подписан её же центром, и его кладут в `MAIL_CA` строкой в PEM.

Без `MAIL_HOST` и `MAIL_FROM` канал выключен: письма продолжают копиться в
очереди и уйдут все разом, когда почту настроят, а интерфейс честно
говорит, что ссылку надо передать руками. Что ушло и дошло ли —
`GET /api/v1/mail` (требует `member.invite`).

Клиент SMTP свой, без зависимостей: протокол отправки письма — это
десяток строковых команд и разбор трёхзначных кодов, и тянуть ради него
дерево пакетов в рабочее пространство компании незачем.

## Переписку нельзя переписать задним числом

Правка сообщения перезаписывала текст молча: обещание «отправлю до
пятницы» превращалось в «посмотрю на неделе», и доказать обратное было
нечем — в продукте, чей журнал показывает, кто и когда раскрыл пароль из
сейфа.

Прежний текст хранится целиком (`message_versions`), а не разницей:
разницу надо уметь читать, а спор идёт о том, что человек написал тогда.
Версия, запись в журнал и сама правка — одна транзакция: след, который
можно потерять отдельно от изменения, не след. Правка, ничего не
меняющая, версии не плодит.

В журнал уходит факт и размер правки, но не текст: журнал читают те,
кому переписка не адресована. Пометка «изменено» стала кнопкой —
`GET /api/v1/messages/{id}/versions` показывает, что там стояло раньше,
тому, кто видит беседу.

## Срок доступа

Приглашённый представитель заказчика оставался в чужом пространстве
навсегда: проект закончился год назад, а доступ к перепискам и файлам
остался, и руками его никто не вспомнит закрыть.

Срок ставится в момент приглашения — тогда, когда зовущий ещё помнит,
зачем и на сколько, — и переезжает с приглашения на членство при входе:
приглашение одноразовое, а находиться внутри человек продолжает. Менять
его потом можно через `PUT /api/v1/people/{id}/access`.

Проверка стоит в чтении сессии, а не в сборщике: сборщик может не
запуститься, а этот запрос выполняется на каждое обращение к серверу.
Поэтому истёкший срок закрывает и живую сессию, и повторный вход — в тот
же миг. Себе и владельцу срок не ставится: компания не должна однажды
остаться без того, кто ею распоряжается.

## Развёртывание

`Dockerfile` и `docker-compose.yml`. Раньше инструкция состояла из
«поставьте Node, поднимите PostgreSQL, накатите миграции руками» — трёх
мест, где можно ошибиться, и ни одного, где ошибку заметят.

    cp .env.example .env    # заполнить POSTGRES_PASSWORD и VAULT_KEY
    docker compose up -d

Миграции накатываются отдельным разовым контейнером, а не при старте
приложения: так они не выполняются одновременно двумя копиями при
масштабировании, и падение наката не выглядит как падение сервиса.
Приложение работает не от root, а `HEALTHCHECK` спрашивает `/readyz`, то
есть готовность, а не факт запуска процесса. Клиент PostgreSQL лежит в
образе намеренно: копия снимается тем же образом, что и работает, и
версия `pg_dump` совпадает с сервером сама собой.

## Резервное копирование

    npm run backup                                   # копия в data/backups
    npm run restore -- --from data/backups/… --check # проверка восстановления

Копия — это база (`pg_dump --format=custom`) и файлы вложений рядом, в
одной папке с описью. По отдельности они бесполезны: база без файлов —
это сообщения со ссылками на вложения, которых больше нет, а файлы без
базы — папка безымянных ключей. В описи лежит контрольная сумма, и
восстановление сверяет её до того, как что-нибудь тронет: «развернулось
наполовину» хуже, чем «не развернулось».

`--check` разворачивает копию во временную базу, считает строки и
удаляет её за собой. Копия, которую ни разу не разворачивали, — не
копия, а файл; про это узнают в тот единственный день, когда она нужна.
Восстановление в непустую базу требует `--force`: восстановление поверх
живого пространства — самая дорогая опечатка из возможных.

Хранилище в S3 копируется средствами провайдера — выдумывать поверх него
свою синхронизацию значит делать хуже.

## Метрики

`GET /metrics` в текстовом формате Prometheus, без зависимостей: счётчик
и гистограмма — это десяток строк. Наружу идут число запросов и их
длительность по маршруту и коду, глубина обеих очередей (почта и
вебхуки), пул соединений с базой и число живых сокетов.

Метрики намеренно не содержат ни людей, ни пространств: то, что уходит
в мониторинг, живёт там годами и видно всей эксплуатации. Единственная
подробность — маршрут с подставленным `:id`. `METRICS_TOKEN` закрывает
маршрут, если задан; в закрытом контуре требовать секрет ради секрета
только мешает.

## Наблюдаемость

Каждый запрос оставляет в журнале одну строку JSON: время, уровень, признак
запроса (`reqId`, он же возвращается заголовком `x-request-id`), метод,
маршрут с подставленным `:id`, код, время ответа, пространство, человек и
адрес. Уровень считается по коду, который реально ушёл клиенту. Строка
одна, потому что в аварии её читают `jq` и `grep`, а не глазами:
`jq 'select(.ms>1000)'`, `jq -r .wsId | sort | uniq -c`.

`/healthz` отвечает «процесс жив» и к базе не ходит. `/readyz` спрашивает
базу и хранилище на деле и отдаёт 503, когда спрашивать бесполезно: там же
состояние пула (`total`/`idle`/`waiting`), память, время работы и число
живых сокетов. Мониторингу нужны оба: первый для перезапуска, второй для
снятия трафика.

Отказ инфраструктуры — база не отвечает, диск переполнен, каталог закрыт —
отвечает 503 `STORAGE_UNAVAILABLE`, а не 400 с внутренним адресом или
путём на диске. У запросов к PostgreSQL есть сроки: `PG_STATEMENT_TIMEOUT_MS`
(15 с), `PG_LOCK_TIMEOUT_MS` (5 с), `PG_CONNECT_TIMEOUT_MS` (3 с).

Вход и неудачная попытка входа пишутся и в журнал эксплуатации, и в журнал
рабочего пространства — с причиной и адресом. Отключение приёмника вебхуков
после череды неудач тоже: это событие, о котором иначе узнают от заказчика.

## Сроки хранения

Раз в шесть часов (`RETENTION_INTERVAL_MS`) уборщик удаляет то, что уже
отработало: просроченные и отозванные сессии, использованные ссылки на смену
пароля, прочитанные и убранные в архив уведомления, доставленные и мёртвые
доставки вебхуков, опубликованные события очереди, от которых не осталось
доставок. Сроки — `RETENTION_DAYS` (90 дней) и `RETENTION_NOTIFICATION_DAYS`
(30 дней); `RETENTION_ENABLED=false` выключает уборку целиком.

Журнал (`audit_events`) и сама работа — сообщения, задачи, встречи, файлы —
не чистятся никогда: журнал ведут ровно затем, чтобы он пережил тех, о ком
написан, а работу удаляет человек, а не уборщик.

## Журнал и увольнение

`GET /api/v1/audit` отдаёт журнал рабочего пространства — кого пригласили,
кто вошёл, кому выписали ссылку на смену пароля, кто раскрыл пароль из
сейфа, что стало с задачами. Листается курсором (`cursor`), отбирается по
виду записи (`type`) и по человеку (`actor`). Читают владелец, администратор
и руководитель — право `audit.read`. В интерфейсе это плитка «Журнал».

`PATCH /api/v1/workspace` меняет название компании и рабочего пространства,
`POST /api/v1/workspace/owner` передаёт владение: новый владелец получает
все права, прежний остаётся администратором. Оба маршрута — за правом
`organization.manage`, единственным, чем владелец отличается от
администратора. В интерфейсе это плитка «Компания».

`POST /api/v1/people/{id}/deactivate` и `/reactivate` — увольнение и
возвращение на работу: право `member.manage` (владелец и администратор) и
только в отношении того, кто ниже по лестнице ролей; владельца и себя
уволить нельзя. Доступ закрывается немедленно — открытые сессии обрываются
в той же транзакции, — а задачи, сообщения и доказательства остаются на
месте. Событие уходит в журнал.
